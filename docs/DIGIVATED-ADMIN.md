# Owner dashboard

Open `/admin` on the Digivated site. This is a private, single-owner dashboard for submissions, articles, and additional products. It does not create community accounts or reuse buyer licenses, payment cookies, or payment environment variables.

## One-time setup

The repository still uses Astro static pages and Vercel Node functions. Dashboard records and sessions use the same dedicated Upstash Redis REST database as submissions. No new production dependencies or framework changes are needed.

Create a private Upstash Redis database and configure these **server-only** Vercel environment variables:

| Variable | Value |
| --- | --- |
| `SUBMISSIONS_REDIS_REST_URL` | The dedicated database's HTTPS REST endpoint |
| `SUBMISSIONS_REDIS_REST_TOKEN` | Its write-capable REST token |
| `DIGIVATED_ADMIN_PASSWORD_HASH` | Generated hash from the setup helper below |
| `DIGIVATED_ADMIN_SESSION_SECRET` | Separate random secret generated by the helper |
| `DIGIVATED_ADMIN_ORIGIN` | Exact HTTPS site origin, with no path; defaults to the existing production domain |
| `SUBMISSIONS_ORIGIN` | Exact HTTPS site origin for submissions; defaults to the existing production domain |

Choose a unique password of at least 16 characters and keep it in a password manager. In a local Bash terminal at the repository root, run:

```bash
read -rs -p 'New owner password: ' digivated_owner_password
printf '%s' "$digivated_owner_password" | node scripts/setup-admin.mjs
unset digivated_owner_password
```

The helper writes the hash and a fresh session secret into a new mode-0600 file under ignored `.private/`. Add those two values to Vercel; do not commit the file or put secrets in chat. The plaintext password is not written to that file. These values are entirely separate from `SESSION_SECRET`, `EDITION_KEY`, and every existing payment setting. No `PUBLIC_` prefix is used.

Use a separate database and credentials for preview. Set both origin variables to the exact preview alias you will open. Redeploy after setting variables. With missing configuration the dashboard fails closed and explains setup is required; it never uses a default password. A Vercel deployment-protection sign-in, when enabled, is separate from dashboard sign-in.

After setup, submit a real test project through `/submit-project`, sign into `/admin`, and check its arrival. Approve, inspect the public directory, then archive your test. No live Redis connection or admin credentials were provisioned as part of source implementation.

## Review submissions

1. Choose **Submissions**, then **Review project**.
2. Inspect the submitted URL, image, email, private notes, and permission confirmation.
3. Edit the public name, creator, description, category, and verified creator-profile URL if needed. Email and notes remain private.
4. Choose **Approve & publish**, **Reject**, or **Archive**. Approval publishes immediately to Discover on the next page load. Archiving/rejection removes the project and its image from public API access immediately. Pending items never appear publicly.
5. After approval, choose **Make Featured Build** to replace the current homepage feature. Only one project can have this status. The old feature remains approved.
6. Check **Digivated Pick** and save to include an approved project in Picks.

Use search and status filters for the loaded records; **Load more** retrieves another 25 records. **Refresh** reloads the latest list. Edits include revision checks, so an old tab cannot silently overwrite newer changes. If a conflict occurs, close/reopen the item and reapply your changes. Save messages explicitly say whether the item is public. No export command or redeployment is needed for normal moderation.

## Write articles

Choose **Articles → New article**. Set a unique lowercase URL slug, title, description, category, publication date, reading time, and article text. Optional cover images accept JPG/PNG/WebP up to 500 KB. Add related articles by their comma-separated slugs.

Use blank lines for paragraphs and `## ` at the start of a block for section headings. This is a plain-text editor; arbitrary HTML and scripts are not rendered. Save as **draft** to keep it private. Choose **Publish** when ready. Set **archived** to remove it from public access. The slug remains fixed after the first save.

Published articles appear in Resources and the homepage's latest-resources section. Detail links use `/resources/read?slug=your-slug` within the existing static Astro deployment. The page fetches only published content. Draft/unpublished direct links return unavailable, and draft cover images cannot be fetched publicly.

## Manage products

Choose **Products → New product**. Enter its unique identifier, name, description, optional label/image, and full HTTPS/HTTP URL to its existing product page. Publish to add it to Products, or save a draft. Archive to remove the additional product from the public list.

**The existing UI/UX Prompt Packet is locked.** It remains the static first product and uses its exact preserved product page and Gumroad destination. The API rejects edits using its reserved identifier and prevents additional entries from targeting its protected URLs. The dashboard never creates checkout sessions, sets prices, changes payment IDs, or modifies product/provider settings. Other products must already have their own working destination.

## Security and privacy

- Server-side authentication is required on every admin read/write, including private record/image retrieval.
- Passwords use salted scrypt hashes; sign-in has an independent Redis limit of five attempts per IP per 15 minutes.
- Sessions expire after eight hours. They use random opaque tokens in a Secure, HttpOnly, SameSite=Strict `__Host-digivated-admin` cookie; only token hashes are stored in Redis.
- State-changing requests require the configured Origin plus a session CSRF token. No session credentials are saved in browser localStorage.
- Sign-out revokes the Redis session. Changing the admin password hash or session secret invalidates existing sessions. There is no public password-reset or registration route.
- Admin responses are private/no-store; the admin page has no analytics or third-party scripts and is marked noindex. Private values are not logged by the new handlers.
- Public project/article/product responses contain only explicit publication fields. Emails, notes, consent evidence, passwords and sessions are never included.
- Uploaded images remain private until the item is approved/published; public image requests check current publication status and are not cached by the endpoint.
- Review links and images before publishing. The dashboard does not send email or social reposts. Archiving does not recall content someone previously viewed or downloaded.

## Operations and limitations

- Back up the private Redis database using the provider's export/backup facilities. Do not commit private backups or `.private/` files.
- Pending/rejected records are retained for owner review; there is no automatic deletion or retention job. Establish an owner retention practice in the database console.
- Public project/resource collections load with JavaScript and live API requests. The protected packet page and checkout links still render statically. Dynamic article content has limited initial server-rendered SEO/social metadata compared with prebuilt article routes.
- The old JSON resource catalog and static resource detail generator remain for compatibility, but dashboard publishing uses the database. Do not maintain the same article in both places.
- The existing moderation CLI now uses the same atomic publishing operation. Its `export` remains an optional snapshot tool, not a required publishing step.
- Setup requires the new storage and admin variables. Local integration tests do not establish that production Upstash credentials or Vercel routing are configured correctly.

For reproducible integration tests, start an isolated local Redis on a nonproduction port and set `DIGIVATED_TEST_REDIS_PORT`. Tests use only loopback connections and dedicated Redis databases 13 and 14, which they clear. `node --test tests/admin.test.mjs` exercises real Lua operations; `npx playwright test tests/browser/admin.spec.ts` tests the browser-to-handler-to-Redis lifecycle. The dedicated GitHub workflow provides its own disposable Redis service.
